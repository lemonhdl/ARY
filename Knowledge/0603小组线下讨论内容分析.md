# 0603 小组线下讨论内容分析

来源：`0603小组线下讨论录音转录文档.md`

这次讨论已经抓住了 ARY 当前阶段的几个关键问题：PRD 怎么拆、数据安全怎么证明、PoC 怎么做、Riding Record 素材怎么留。整体上，它处在“形成方向”的阶段，不适合直接当最终 PRD，需要继续校正概念、补齐模型和收敛表达。

## 讨论得比较充分的内容

### PRD 分析方法已经基本成型

讨论中形成了一条可用的方法链：

> 场景 → 角色 → 职责 → 用例 → 数据 → 功能需求 / 非功能需求

这比直接罗列功能更稳。ARY 不是普通网站，很多需求需要从 Organizer、Rider、平台、Agent、评审方之间的关系里挖出来。

后续可以把这条方法作为内部需求分析方法，但不要直接把逐字稿里的口语表达搬进对外 PRD。

### 数据安全 PoC 的实验逻辑比较清楚

讨论里形成了“开关实验”的思路：

1. 只启动平台，提交后显示数据缺失。
2. 启动组织方本地进程，提交后得到评测结果。
3. 关闭组织方进程，再提交又变成数据缺失。

这个思路很有价值。它比“我们不保存数据”这种口头声明更强，因为它用行为证明平台没有提前持有可用评测数据。

### “不持久化”不是“不用数据库”这一点讨论得对

讨论里已经意识到，账号、成绩、赛程等平台自身数据需要持久化；不持久化主要针对组织方敏感评测数据。

后续应固定为：

- 平台可以持久化账号、权限、Race 元数据、提交记录、公开结果、Riding Record 摘要。
- 平台不应持久化组织方完整评测数据、未公开题目、私有评审依据、敏感原始材料。
- 日志、缓存、临时文件也可能构成持久化，不能忽略。

### Riding Record 和过程素材的重要性被明确提出

讨论后半段提到，需要记录 Agent 使用过程、Prompt、Agent output、Steering、commit 历史、模块生长过程，作为后续 Riding Record 素材。

这很关键。它把项目从普通评测平台拉回 ARY。ARY 的核心不是“交答案得分”，而是“展示和评价人如何驾驭 Agent 完成任务”。

这个方向已经出现，但具体模型还没展开。

### 短期分工已经有雏形

讨论最后形成了几块工作：

- 验收清单和风险分析
- 项目概述和 PoC
- Rider 角度的角色、用例、功能需求和数据类型
- 非功能需求
- 系统模型 / PoC 相关内容

这说明小组已经开始从讨论问题转向分配产出。不过分工仍然较粗，需要进一步落成明确的文档责任和交付边界。

## 需要纠正或谨慎处理的内容

### ARY 被多次说成普通比赛平台或 OJ 逻辑

逐字稿里反复出现“题解”“评分”“排行”“每天放一道题”等表达。这些可以作为类比，但不能成为 ARY 主线。

风险是 PRD 写着写着变成 LeetCode 加 Agent 外壳。

需要纠正为：

- ARY 的核心对象是 Agent Riding Race。
- 评价重点是 Rider 如何使用、约束、纠偏和验证 Agent。
- 提交和评测只是平台流程的一部分，不是产品核心。
- 排行榜可以有，但不能压过 Riding Record。

### “Organizer 直接把数据传给 Rider”是错误方向

讨论中一开始出现过 Organizer 直接把数据传给 Rider 的想法。后续已经被纠正为：Rider 提交内容，Organizer 在本地用数据评测，再返回结果。

后者才是合理方向。前者会破坏组织方数据安全，因为敏感数据一旦给到参赛方，就很难控制复制、泄露和二次传播。

### “平台没有数据就是去中心化数据主权”过于简化

讨论后段把去中心化理解为“平台没有数据，数据留在组织方”。这个方向不算错，但太窄。

更准确的说法应是：

- 去中心化不是平台完全没有数据。
- 平台仍然需要保存必要的公开数据、账号数据、提交状态、评价摘要、Riding Record 摘要。
- 数据主权重点在于完整敏感数据由数据拥有方控制，平台只获得被授权的最小必要信息。
- Organizer、Rider 都可能拥有自己的本地数据主权。
- 平台提供组织、展示、评测协调、权限和回放能力，而不是吞掉所有原始数据。

### “账号密码需要持久化”的表述不安全

讨论中提到账号密码需要持久化。这个说法要改。

更安全的表达是：

- 不能持久化明文密码。
- 应持久化密码哈希、身份凭证、session/token 元数据。
- 如果使用第三方登录，可以不保存密码，只保存用户标识和授权状态。
- 账号数据也需要权限控制、最小化保存和删除策略。

### “Viewer 这次不重要”需要限制语境

如果只看本周 PoC，可以暂时不优先做独立 Viewer 模块。但从 ARY 平台整体看，Viewer / 评审方视角不能忽略。

原因是：

- ARY 要展示 Riding Record。
- 老师或评审方就是一种 Viewer。
- 平台可交付性依赖“别人能点开看懂”。
- 数据安全证明也需要给外部评审看，而不是只在内部解释。

所以更准确的说法是：本周不优先做独立 Viewer 模块，但 Viewer 视角在后续需求和展示设计中必须保留。

### “Demo 录屏都可以解决”不够准确

录屏可以作为交付材料，但 PoC 不能只有录屏。至少应该有：

- 可运行页面
- 可点击流程
- 可复现的启动命令
- 可验证的数据安全实验
- 自动或半自动验收脚本

现在 PoC 已经走向这个方向，这是对“录屏即可”的修正。

### “Agent 等同用户本人访问”不能作为长期设计结论

短期 PoC 可以把 Agent 操作视为用户操作。但长期系统设计不能直接跳过 Agent 权限问题。

未来要考虑：

- 人类 Rider 和其 Agent 是否有不同权限。
- Agent 是否只能读取某些材料，不能提交最终答案。
- Agent 操作是否需要被记录。
- Agent 代理行为是否需要用户确认。
- 如何防止 Agent 获得超出 Rider 授权的数据。

## 还没有讨论到或明显不足的内容

### 角色体系还不完整

目前主要讨论了 Organizer 和 Rider，但 ARY 至少还需要区分：

- Organizer / 组织方
- Rider / 参赛者
- Agent / 被驾驭的智能体
- Judge / 评审方
- Viewer / 观看者或外部评审
- Platform Admin / 平台管理员
- Local Data Processor / 组织方本地评测进程
- Record Curator / Riding Record 整理者

这些角色的权限、目标、痛点和用例还没有系统展开。

### 数据分类还没有形成表格

后续至少需要列出：

| 数据类型 | 拥有者 | 是否进入平台 | 是否持久化 | 谁能看 | 用途 |
|---|---|---|---|---|---|
| 组织方原始数据 | Organizer | 否 | 否 | Organizer | 本地评测 |
| 题目公开材料 | Organizer | 是 | 是 | Rider / Viewer | 赛事展示 |
| Rider 提交 | Rider | 是 | 视策略而定 | Rider / Organizer / Judge | 评测 |
| 评测结果 | Organizer | 是 | 是 | Rider / Organizer / Judge | 反馈 |
| Riding Record 摘要 | Rider / 平台 | 是 | 是 | Viewer / Judge | 过程展示 |
| 完整 Agent 会话 | Rider | 可选 | 可选 | 取决于授权 | 回放和分析 |

这张表比口头说“哪些持久化、哪些不持久化”更适合进入需求分析或系统设计。

### Riding Record 的数据模型还没讨论清楚

目前只说要记录 Prompt、Agent output、Steering、commit 历史，但还没回答：

- Riding Record 是自动生成还是人工整理。
- 原始 session 是否上传。
- 是否只上传摘要。
- 谁有权编辑 Record。
- Record 是否可以被回放。
- Record 是否可被评分。
- 如何证明 Record 没被篡改。
- 如何处理敏感 prompt、密钥、路径、内部数据。

这是 ARY 的核心模块，后续必须单独展开。

### 评测模型还没有讨论

讨论里只说“评分”“多个维度”，但没明确 Agent Riding Race 到底评什么。

后续需要考虑：

- 结果正确性
- Prompt 质量
- Steering 质量
- 验证意识
- 任务拆解能力
- Agent 工具使用能力
- 成本和效率
- 安全边界遵守
- 可复盘性
- 团队协作贡献

如果没有评价模型，ARY 容易退化为普通提交评测平台。

### 系统架构还没有成型

讨论里提到了平台进程、Organizer 进程、网页、转发系统，但还没有系统模型。

至少需要画出：

- 平台前端
- 平台后端
- 平台数据库
- Organizer 本地评测服务
- Rider 本地 Agent 环境
- Riding Record 采集 / 导入模块
- 回放展示模块
- 权限与审计模块

还要标清楚数据流和信任边界。

### 权限模型没有展开

后续要回答：

- Organizer 能看哪些 Rider 数据。
- Rider 能不能看别人的提交。
- Viewer 能看哪些 Record。
- Judge 能不能看完整会话。
- 平台管理员能不能看组织方敏感数据。
- Agent 是否继承用户权限。
- 匿名参赛如何实现。
- 多赛事之间如何隔离。

这是数据安全的一部分，不能只靠“不持久化”解决。

### 日志、缓存、临时文件没有讨论

讨论集中在数据库和外存，但实际系统里泄露常常来自：

- 请求日志
- 错误日志
- 临时文件
- 浏览器缓存
- API 调试输出
- 评测过程 stdout / stderr
- session trace
- 上传文件残留

后续如果写数据安全，必须把这些也纳入“不保存敏感数据”的边界。

### 多组织方和多赛事隔离没有展开

讨论里提到平台不只面对一个客户、多场比赛，但还没展开。后续至少需要考虑：

- 不同 Organizer 的数据隔离
- 不同 Race 的权限隔离
- 同一 Rider 参与多个 Race 的数据边界
- 多租户下的资源调度
- Organizer 自定义公开范围

### 验收标准还没有真正定下来

讨论里提到验收标准和风险分析，但还停留在“要有人写”的层面。

后续要把验收标准写成可检查的句子，例如：

- 未提交前不展示评测结果。
- 未提交前不展示 Riding Record 详情和回放。
- Organizer 评测进程未启动时提交显示数据缺失。
- Organizer 评测进程启动后提交返回结果。
- Organizer 评测进程关闭后再次提交恢复数据缺失。
- 页面不暴露内部路径、版本号、服务请求、私有数据名。
- Riding Record 页面能展示 Prompt、Agent Output、Steering、Riding Signal。

## 总体判断

这次讨论最有价值的成果有三个：

1. 找到了 PRD 分析方法：从角色、职责、用例和数据推需求。
2. 找到了数据安全 PoC 的实验性证明方法：平台进程和组织方本地进程分离，用开关证明未持久化。
3. 意识到 Agent Riding 过程需要被记录、整理和回放，不能只做普通评测网站。

主要问题也有三个：

1. ARY 和普通 OJ 的边界还没有完全稳住。
2. 去中心化数据主权、权限、持久化这些概念还比较粗。
3. Riding Record、评测模型、系统架构和权限模型还没有系统展开。

下一步适合做的不是继续扩写逐字稿，而是把本分析中的“已确认口径”“需要纠正的说法”“后续必须补的问题”分别对接到需求分析报告、PoC 迭代和系统建模文档中。
