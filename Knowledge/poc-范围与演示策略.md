# PoC 范围与演示策略

## 当前时间约束

从 2026-06-03 开始计算，PoC 可用时间大约只有 4 天。

因此这次 PoC 不追求完整平台，也不追求完善的接口设计和底层实现。

目标是做出一个可以运行、可以点击、可以让老师看懂关键证明点的小型原子系统。

## PoC 的优先级

优先级从高到低：

1. 老师能在 Demo 上点出关键流程
2. Demo 能证明 GRS 001 的关键假设
3. 页面能让评审快速看懂 Organizer 侧和 ARY 侧的数据边界
4. 系统能展示创建、披露、组织、展示 Race 的基本路径
5. 底层实现足够支撑演示即可

低优先级：

- 完整接口设计
- 完整数据库设计
- 真实生产级权限系统
- 完整赛事执行系统
- 完整指导骑行、评审、复盘子系统
- 复杂部署和高可用能力

## 允许的实现方式

在 4 天 PoC 语境下，可以接受：

- mock implementation
- mock data
- 本地 JSON 文件模拟数据库
- 本地服务模拟 Organizer evaluator
- 写死少量 Race 示例
- 简化的用户和角色切换
- 简化的公开投影和排行榜

这些实现方式不等于产品最终方案。

它们的作用是帮助 Demo 跑通，证明产品逻辑和数据边界成立。

## 原子系统定义

这个 PoC 的原子系统可以理解为：

一个最小可运行 Demo，让评审完成一次简化 Race 浏览、题解提交、远端评测、结果展示和数据安全证据查看。

它至少应包含：

1. Organizer 侧私有数据区域
2. ARY 侧公开 Race 展示区域
3. Rider 提交入口
4. Organizer evaluator 计算结果
5. ARY 排行榜或结果展示
6. 数据安全证据页

## 演示判断标准

老师点 Demo 时，应能看到：

- Race 可以被创建或展示出来
- Race 的完整私有数据在 Organizer 侧
- ARY 侧只展示公开元数据或公开投影
- Rider 可以提交题解
- 评测发生在 Organizer 侧
- ARY 只拿到分数和公开结果
- ARY 侧看不到测试数据或隐藏规则

## 对 PRD 和系统设计的影响

对外 PRD 可以把 PoC 表述为“关键假设验证原型”。

不要把 mock implementation 包装成生产级实现。

可以明确说明：

- PoC 使用 mock data 和本地服务证明数据流
- 真实产品中可以替换为正式数据库、认证系统和 Organizer 部署环境
- 这次验证的重点是数据主权边界和平台能力是否能够同时成立

## 设计原则

这次 PoC 不用追求做大。

应该追求路径短、证据清楚、点击顺畅。

如果某个功能不能帮助证明“数据在 Organizer 侧，ARY 仍能展示和组织 Race”，就先不做。
