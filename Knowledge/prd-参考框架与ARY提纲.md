## 1 项目概述

### 1.1 项目名称

ARY GRS 001：数据安全的 Race

### 1.2 项目背景

写清楚：

- ARY 是 Agent Racing Yard
- GRS 001 是 ARY 创世骑行系列赛第一场 Race
- 本次不是完整实现 ARY
- 本次重点是产品定义和技术 PoC
- 核心问题是数据安全和数据主权

### 1.3 参考资料与现有方案分析

这里可以替换参考报告的“竞品分析”。

可分析对象：

- 普通中心化竞赛平台
- Kaggle 类数据竞赛平台
- GitHub Classroom 类作业提交平台
- 本地评测或远端评测方案
- 联邦学习中的数据不出域思想

重点不是写很多竞品，而是推出我们的机会：

- 普通平台往往要求 Organizer 上传完整数据
- 对政务、企业、研究数据等场景不现实
- ARY 要证明数据留在 Organizer 侧也能组织和展示 Race

### 1.4 项目目标

建议写成 4 个目标：

1. 证明 Race 数据可以留在 Organizer 侧
2. 证明 ARY 不需要持久化完整 Race 数据
3. 证明 ARY 仍能创建、披露、组织、展示 Race
4. 证明展示内容来自 Organizer 主动披露的公开元数据或公开投影

### 1.5 本次 PoC 范围

写清楚本次做什么：

- Race 创建或导入
- Race 公开展示
- Rider 提交题解
- Organizer evaluator 远端评测
- ARY 展示分数和排行榜
- 数据安全证据页

写清楚本次不做什么：

- 完整赛事执行系统
- 指导骑行
- 成果评审
- 骑行复盘
- 生产级权限系统
- 生产级数据库和部署

### 2.2 场景 角色 职责 用例

用表格写：

| 场景 | 角色 | 职责 | 用例 | 推出的数据 |
|---|---|---|---|---|
| Organizer 举办 Race | Organizer | 提供赛题和评测数据 | 创建 Race | Race 私有数据、公开元数据 |
| Rider 参加 Race | Rider | 提交题解 | 提交作品 | 参赛题解 |
| 平台展示 Race | ARY | 展示公开内容 | 展示 Race 详情 | 公开投影 |
| 平台请求评测 | Organizer evaluator | 使用本地数据计算结果 | 返回分数 | score、public_result、hash |

## 3 功能需求

建议沿用参考报告的编号写法。

每个功能写：

- 优先级
- 描述
- 功能点
- PoC 实现说明
- 验收标准

### 3.1 设计理念：数据不出域与公开投影

说明 ARY 的设计理念：

- Organizer 保留完整 Race 私有数据
- ARY 保存公开元数据、公开投影、结果摘要
- 敏感数据不在 ARY 平台持久化
- ARY 通过 Organizer evaluator 使用数据
- 展示内容来自 Organizer 主动披露

### 3.2 核心功能

#### 3.2.1 Race 创建与导入 F001

Organizer 创建或导入一个 Race。

PoC 可以使用 mock Race 数据。

验收点：ARY 页面能显示 Race，但不保存完整私有数据。

#### 3.2.2 Race 披露与公开投影 F002

Organizer 选择哪些内容可以公开。

公开内容包括：

- Race 标题
- 简介
- 规则摘要
- 截止时间
- 公开说明
- 数据版本 hash

验收点：ARY 只展示公开投影，不展示隐藏测试数据和私有材料。

#### 3.2.3 Rider 查看与提交 F003

Rider 查看 Race 信息并提交题解。

验收点：提交物能进入 ARY，且可用于后续评测。

#### 3.2.4 Organizer 侧远端评测 F004

ARY 将题解发送给 Organizer evaluator。

Organizer evaluator 使用本地测试数据计算分数。

验收点：ARY 只收到 score、public_result、data_version_hash。

#### 3.2.5 结果摘要与排行榜 F005

ARY 展示分数摘要和排行榜。

验收点：排行榜能展示结果，但不暴露测试数据。

#### 3.2.6 数据安全证据页 F006

展示 Organizer 侧和 ARY 侧分别保存了什么。

验收点：老师可以点开页面看到 ARY 没有保存敏感数据。

#### 3.2.7 简化角色与访问控制 F007

PoC 中可以用简单角色切换模拟访问权限。

验收点：Rider 不能看到 Organizer 私有数据，也不能看到其他队伍未公开题解。

### 3.3 界面与交互

建议写 Demo 页面：

- Race 列表页
- Race 详情页
- Rider 提交页
- 评测结果页
- 排行榜页
- 数据安全证据页

### 3.4 数据管理

写清楚：

- ARY 持久化哪些数据
- ARY 不持久化哪些数据
- Organizer 侧保存哪些数据
- mock data 在 PoC 中如何模拟真实边界

## 5 数据需求与安全机制

这一章建议单独保留。它是 ARY 与普通 PRD 最大的差异。

### 5.1 数据分类表

| 数据类型 | 数据归属 | 是否在 ARY 持久化 | 是否公开 | 安全机制 |
|---|---|---|---|---|
| Race 私有数据 | Organizer | 否 | 否 | 数据不出域 |
| 测评样例或隐藏测试数据 | Organizer | 否 | 否 | Organizer evaluator 本地读取 |
| 公开元数据 | Organizer 主动披露 | 是 | 是 | 公开投影 |
| 参赛题解 | Rider | 是 | 默认不公开 | 权限控制、时间锁 |
| 分数摘要 | ARY | 是 | 可公开 | 结果投影 |
| 排行榜 | ARY | 是 | 可公开 | 公开展示 |
| 数据版本 hash | Organizer | 是 | 可公开 | 完整性证明 |

### 5.2 数据流说明

建议画图并配文字：

1. Organizer 本地保存私有数据
2. Organizer 向 ARY 披露公开投影
3. Rider 在 ARY 提交题解
4. ARY 请求 Organizer evaluator
5. Organizer evaluator 本地计算
6. Organizer evaluator 返回分数和公开结果
7. ARY 展示排行榜和结果摘要

## 8 验收标准

### 8.1 功能验收

- Race 能展示
- Rider 能提交
- Organizer evaluator 能返回结果
- ARY 能展示排行榜
- 数据安全证据页能打开

### 8.2 数据安全验收

- ARY 侧看不到测评样例或隐藏测试数据
- ARY 存储中只有公开元数据、公开投影、提交物、分数摘要
- 评测结果来自 Organizer evaluator
- 日志或展示中不出现敏感数据

### 8.3 PoC 演示验收

- 老师可以按固定路径点击完成演示
- 每一步都能说明它证明了什么
- Demo 不因 mock data 影响关键证明

## 9 风险分析

建议表格：

| 风险类型 | 风险描述 | 影响等级 | 缓解措施 |
|---|---|---|---|
| 范围风险 | 想做完整 ARY，导致 4 天内做不完 | 高 | 只做 GRS 001 数据安全 PoC |
| 证明风险 | Demo 有功能，但看不出数据安全证明 | 高 | 增加数据安全证据页和数据流图 |
| 表达风险 | PRD 写成普通竞赛平台需求 | 高 | 强调数据主权、公开投影、Organizer 侧数据 |
| 实现风险 | 接口和底层实现过度设计 | 中 | 使用 mock implementation 和 mock data |
| 演示风险 | 老师点 Demo 时路径不清楚 | 中 | 设计固定演示脚本和少量关键页面 |

## 使用建议

我们的 PRD 可以参考 TimeFlow 的结构，但不要照搬它的内容重点。

TimeFlow 的重点是日程管理功能完整性。

ARY GRS 001 的重点是数据安全证明。

因此 ARY PRD 应保留这些结构：

- 项目概述
- 功能需求
- 非功能需求
- 约束条件
- 系统模型
- 验收标准
- 风险分析

但要新增或强化这些内容：

- 本次 PoC 范围
- 场景 角色 职责 用例
- 数据分类
- 数据安全机制矩阵
- Organizer 侧和 ARY 侧的数据边界
- 数据流图
- 数据安全证据页
