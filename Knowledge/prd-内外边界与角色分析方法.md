# PRD 内外边界与角色分析方法

## 已确认理解

PRD 是产品需求文档。

本项目讨论 PRD 时要区分两层内容。

一层是内部分析。

内部分析可以包含：

- 真实讨论过程
- 竞标策略
- 取舍
- 风险
- 不适合直接展示的判断
- 对其他小组可能方案的预判

另一层是对外展示的 PRD。

对外 PRD 面向评审方或投资方。

这次作业里，老师可以类比为投资方，小组可以类比为竞标方。

对外 PRD 应该展示：

- 产品需求
- 用户价值
- 系统边界
- PoC 证明路径
- 数据安全如何成立
- 为什么这个方案值得被选中

对外 PRD 不应该直接展示内部竞标策略，也不应该把所有内部讨论都写进去。

## 分析方法

使用“用户角色 -> 职责 -> 用例”的方法挖需求。

也可以扩展成“场景 -> 角色 -> 职责 -> 用例”。

先列出场景，再识别场景中的用户角色，分析每个角色的职责，最后从职责推出系统用例。

如果场景已经清楚，也可以使用“角色 -> 职责 -> 用例”再补场景。

这样比直接列功能更自然，也更容易发现隐藏用例。

## 场景的作用

场景用于限定需求发生的上下文。

同一个角色在不同场景下可能有不同职责。

同一个职责在不同场景下也可能推出不同用例。

例如 Organizer 在“发布 Race”场景下负责披露公开元数据。

Organizer 在“测评参赛结果”场景下负责提供标准测试数据或运行评测。

这两个场景都会影响数据边界。

## 数据从哪里来

之前讨论中一直困惑“数据长什么样”“会有什么数据”。

现在的判断是：数据不是由投资方直接说清楚的。

提需求的人往往也说不清楚完整数据结构。

软件开发者需要从场景、角色、职责和用例中反推出数据。

也就是说，数据模型不是先验给定的，而是从用例分析中长出来的。

例如“测试数据读取并计算结果”这个用例，会推出：

- 标准测试用例数据
- 参赛提交结果
- 评测输出
- 公开分数
- 排名投影
- 数据版本或 hash
- 可撤回的公开展示内容

这些数据再进一步决定哪些留在 Organizer 侧，哪些可以进入 ARY 的公开投影。

## 角色分类

角色可以分成两类。

### 现实角色

例如：

- 组织方 Organizer
- 参赛方 Rider
- 指导者 Coach
- 评审方 Reviewer
- 公开观看者 Viewer
- 平台运营方

### 代码层抽象角色

例如：

- 数据请求方
- 打分系统
- 滚榜系统
- 测试数据读取器
- 结果计算器
- 公开投影提供方
- 权限校验器

这些抽象角色不一定都写进对外 PRD，但适合用于内部系统分析。

## 示例

组织方的一个职责是提供用于比赛测评的标准测试用例数据。

从这个职责可以推出一个用例：

测试数据读取并计算结果。

继续分析会出现几个问题：

- 标准测试数据是否属于敏感数据
- ARY 是否可以持久化这些数据
- 参赛方是否可以直接看到完整测试数据
- 打分系统在哪里运行
- ARY 展示完整评测记录还是只展示公开结果
- 滚榜系统展示的是实时结果还是 Organizer 主动披露的公开投影

这和本次 GRS 001 的核心要求直接相关。

Race 数据应留在 Organizer 侧。

ARY 只展示 Organizer 主动披露的公开元数据或公开投影。

## 对当前项目的影响

这条讨论影响四类交付：

### PRD

PRD 要用角色、职责、用例组织，而不是只列页面功能。

### 系统设计

系统设计要区分现实角色、系统抽象角色和数据边界。

### PoC

PoC 可以演示测试数据不落在 ARY 侧，但 ARY 仍能展示比赛结果或公开投影。

### 展示

展示时讲产品价值、数据安全和 PoC 证据。

不讲内部竞标策略。
