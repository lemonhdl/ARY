# 数据安全机制与访问权限

## 已确认理解

数据安全的保证方式不只有“不持久化”。

不同数据有不同生命周期和安全要求。

有些敏感数据不应进入 ARY 平台持久化存储。

有些数据必须被平台持久化，但不能被所有人看到。

所以数据安全需要组合多种机制。

## 来源关联

王青项目要求录音中提到，骑手和参赛者需要 access 到某些资产，平台还要组织、回顾、展示成果。

PPT 中也提到作品资产、公开展示页、Riding Replay 和能力资产。

这说明平台不可能完全不保存任何数据。

真正需要设计的是：

- 哪些数据不保存
- 哪些数据要保存
- 保存后谁能访问
- 何时可以公开
- 公开的是原始数据还是公开投影

## 示例：提前提交的题解

场景：参赛队伍提前提交题解。

角色：参赛者 Rider。

职责：在截止时间前提交自己的作品或题解。

用例：提交题解并等待评审或公开。

推出的数据类型：参赛题解。

这类数据和测评样例不同。

参赛题解通常必须持久化。

否则比赛结束后，平台无法证明参赛者当时提交的是什么，也不能要求参赛者之后再提交一份可能不同的内容用于公开展示。

但是参赛题解在比赛过程中不能被其他参赛者看到。

如果被其他参赛者提前看到，会影响公平性。

所以它需要的不是“不持久化”，而是“持久化 + 分用户访问权限 + 公开时机控制”。

## 对应数据安全机制

针对参赛题解，应设计：

- 提交后持久化保存
- 记录提交时间
- 记录提交者和队伍
- 比赛期间仅提交者、队伍成员、授权评审或系统服务可访问
- 其他参赛者不可访问
- 截止或评审后，根据公开规则生成公开投影
- 公开投影可以展示摘要、作品链接、评分、评语或脱敏内容
- 原始题解是否公开由赛事规则或 Organizer 决定

## 和不持久化机制的区别

测评样例适合不持久化在 ARY 平台。

参赛题解适合持久化在 ARY 平台，但做访问控制。

排行榜适合持久化公开结果。

Organizer 私有资料适合保留在 Organizer 侧，只提供公开投影。

因此数据安全不是单一技术，而是按数据类型选择机制。

## 可用机制清单

- 不持久化：适合测评样例、隐藏测试数据、Organizer 私有材料
- 远端计算：适合用 Organizer 本地数据完成评测
- 分用户访问权限：适合提交物、队伍私有资料、评审内容
- 时间锁：适合比赛结束后才公开的题解或成果
- 公开投影：适合对外展示摘要而不暴露原始数据
- hash 或版本号：适合证明数据存在和未被篡改
- 审计日志：适合追踪谁访问过敏感数据

## 对 PRD 的影响

PRD 中的数据安全部分不能只写“ARY 不持久化数据”。

应写成数据分类和安全机制矩阵。

例如：

| 数据类型 | 是否持久化在 ARY | 谁可访问 | 安全机制 |
|---|---|---|---|
| 测评样例 | 否 | Organizer 侧 evaluator | 数据不出域 远端评测 |
| 参赛题解 | 是 | 提交队伍 评审 系统服务 | 权限控制 时间锁 |
| 排行榜 | 是 | 公开或登录用户 | 公开投影 |
| Organizer 私有资料 | 否 | Organizer | 公开投影 hash |

## 对 PoC 的影响

PoC 可以同时展示两类安全机制：

1. 测评样例不持久化在 ARY，远端评测只回传分数
2. 参赛题解持久化在 ARY，但其他队伍无法访问，截止后才生成公开展示

这样比单独展示“不存数据”更完整。
