# Riding Record 去中心化设计

## 基本判断

ARY 不应默认把用户的完整 Riding Record 集中留存在平台上。

更合适的方向是：

- 用户或组织方本地保存完整 Riding Record
- ARY 定义 Riding Record 的数据结构规范
- ARY 提供可在本地运行的服务
- 本地服务读取记录并生成授权后的评价输入、公开投影和回放事件
- 平台基于这些数据完成多维评价和展示

平台的价值不在于占有完整记录，而在于提供标准、评价、回放和展示能力。

## 为什么要去中心化

Riding Record 可能包含大量过程数据：

- Prompt 和上下文
- Agent 输出
- 用户 Steering
- 验证过程
- 项目文件片段
- 任务背景
- 团队协作痕迹

这些内容可能涉及未公开项目材料、组织方规则、团队策略或个人工作习惯。如果平台默认集中保存完整记录，会削弱用户和组织方对过程数据的控制，也会与 ARY 一直强调的数据边界不一致。

去中心化并不表示平台不能评价 Riding Record。它表示平台不应把“评价能力”建立在“长期占有完整原始记录”之上。

## 推荐结构

### 1. 本地记录层

用户或组织方本地保存完整 Riding Record。

记录可以来自 Coding Agent 会话、IDE 插件、命令行工具、项目日志或手工整理材料。

### 2. 数据结构契约层

ARY 定义 Riding Record 的结构。

它需要描述：

- 一次 Riding 的目标
- Rider 与 Agent 的交互事件
- Prompt
- Agent Output
- Steering
- 验证动作
- 结果产物
- 可公开字段
- 不可公开字段
- 评价所需摘要
- 回放所需事件

这个结构是平台、参赛者、本地服务和评审之间的共同契约。

### 3. 本地服务层

ARY 提供可以在用户本地或组织方环境中运行的服务。

本地服务负责：

- 读取完整 Riding Record
- 根据授权范围生成公开投影
- 生成回放事件
- 生成多维评价输入
- 控制哪些字段可以离开本地环境

### 4. 平台评价层

平台接收授权后的数据，而不是默认接收完整原始记录。

平台可以评价：

- 目标设定是否清晰
- Prompt 是否有效
- Steering 是否及时
- Agent 输出是否被验证
- 过程是否可复盘
- 结果是否可靠
- 人和 Agent 的分工是否合理

### 5. 回放展示层

平台展示的是适合公开的 Riding Record 投影。

回放页不必复刻完整原始会话，而应展示经过整理的事件流，让评审看懂一次 Riding 是如何推进的。

## 与当前 PoC 的关系

当前 PoC 使用本地示例数据展示 Riding Record、详情和回放，这是为了验证 ARY 的展示与评测能力。

这个 PoC 不应被理解为未来平台必须集中保存所有 Riding Record。

后续系统设计应把当前 PoC 看作能力验证：

- ARY 能展示 Riding Record
- ARY 能回放 Riding 过程
- ARY 能在提交后触发评价
- ARY 页面不暴露未公开材料

但未来架构应继续向本地记录、本地服务、授权投影和平台评价的方向推进。

## 对后续文档的影响

写需求分析、系统建模和架构设计时，应避免默认写成：

> 用户上传完整 Riding Record 到平台，平台长期保存并评价。

更建议写成：

> 用户或组织方在本地保存完整 Riding Record。ARY 提供数据结构规范和本地服务，在授权范围内生成评价输入和回放投影。平台基于这些投影完成多维评价与展示。

这样更符合 ARY 的去中心化定位，也能延续数据安全证明的主线。
