> URL：https://jcnboj5dg0t7.feishu.cn/docx/X4AqdDG4joXWVfxkRiEcXgIMncd

## 本视角设想的问题

从 Rider（智能体骑手）出发，设想四件事：**我是谁、我拥有什么、怎么做、边界在哪**。

Rider 不是被动接收题目的参赛者——他是这场建造赛的**生产者**。他手中只有项目需求，没有完整私有数据，他必须在组内和同伴协作、组间和其他组竞争，骑在 Agent 这匹马上，完成方案并留下可被检验的 Riding Record。

落脚点是四个证明：

1. Rider 仅有项目需求，仍能和 Agent + 同伴协作完成方案——证明 ARY 不需要持久化完整私有数据
2. 方案经 ARY 沙箱假数据验证后，由 Organizer 真数据评测——证明数据主权在 Organizer 侧
3. Riding Record 记录了人的决策和 Agent 的输出，可区分、可复盘——证明 Agent Riding Skill
4. 组内全透明、组间隔离——证明 ARY 是公平的竞技场

## 1. 角色

### 1.1 主角色：Rider

**Rider 是这一场比赛的参与者与生产者。**

他在一场建造赛里同时扮演三个身份：

| 身份 | 职责 |
| --- | --- |
| **建造者** | 手头只有项目需求，靠驾驭 Agent 产出方案（PRD、PoC、文档） |
| **协作者** | 组内和队友分工、互查 Riding Record、互评互助，留言板沟通 |
| **竞争者** | 组间竞争——谁的方案更好、谁的 Riding Record 更能体现骑行能力 |

Rider 的数据可用范围极窄：**只有项目需求是公开的**。完整私有数据始终在 Organizer 侧，Rider 不直接接触。

### 1.2 交互角色（本视角观察对象，数据安全防范）

- 组员 ：全透明协作。Riding Record 互查互评、互相给 Steering。Agent 可代劳评论和留言板提问。
- Agent ：被驾驭的工具。Rider 下达目标、观察产出、判断正误、干预方向、验收成果。
- ARY 平台 ：
  - 训练场 + 竞技场——展示 Race 信息、收集骑行日志、汇聚贡献面板
  - 安全闸门——沙箱假数据验证方案（死循环、病毒、硬 bug）
  - 公平看板——组间仅公示成绩和排名，方案和 Record 组间隔离
- Organizer ：不可见的裁判。持有真数据，负责最终评测并返回评分。Rider 只在留言板间接与其沟通。
- 评委 ：权限者。可查看各组方案和 Riding Record，在留言板上回复、指导。

## 2. 用例（Use Cases）

`UC-R*` = Rider 用例。标注 Rider 拥有什么数据、依靠什么外部信息、是否产生 Riding Record。

| 编号 | 用例 | Rider 拥有 | 依靠外部 | 产生 Record |
| --- | --- | --- | --- | --- |
| UC-R1 | 理解项目需求 | 需求文档 | Organizer 披露 | ✅ 目标设定记录 |
| UC-R2 | 制定组内分工与骑行计划 | 需求 + 组员列表 | 面板直观分工 | ✅ 计划记录 |
| UC-R3 | 驾驭 Agent 产出方案 | 需求 | Agent 能力 | ✅ 协同全记录 |
| UC-R4 | 观察 Agent 产出并判断 | Agent 输出 | 组员互查 | ✅ 观察与判断 |
| UC-R5 | 干预 Agent、修正方向 | Agent 输出历史 | 组员反馈 | ✅ 干预记录 |
| UC-R6 | 验收 Agent 工作成果 | Agent 产出 | 组员互审 | ✅ 验收记录 |
| UC-R7 | 组内互查 Riding Record | 组员 Record | 无 | ✅ 互评记录 |
| UC-R8 | 留言板提问与回复 | 无 | 评委/Organizer | ✅ 沟通记录（Agent 可代劳） |
| UC-R9 | 提交方案 | 方案 + Record | ARY 沙箱 | — |
| UC-R10 | 查看成绩与排名 | 本组成绩 | Organizer 评分 | — |

### 关键用例展开

#### UC-R3 驾驭 Agent 产出方案

Rider 手头只有项目需求。他需要通过 Agent 协作把方案从无到有建出来。

- 主流程：
  1. 根据 Riding Plan，将任务拆解为 Agent 可执行的工作单元
  2. 向 Agent 下达 Prompt，说明目标和约束
  3. Agent 产出——可能是代码、文档、图表，也可能是废话和幻觉
  4. Rider 阅读 Agent 输出，标注疑点，决定接受、修改还是抛弃
  5. 每一步都自动留下骑行日志（时间戳 + 工作内容 + Agent 原始输出 + Rider 修改）
- 数据边界：Rider 只能基于项目需求向 Agent 描述问题——他没有真数据，也用不着。这本身就证明了数据在 Organizer 侧。
- 安全机制：ARY 自动抓取骑行日志和时间信息，防止事后伪造。面板汇聚组内贡献，一眼可辨谁在骑、谁在划水。

#### UC-R9 提交方案

- 主流程：
  1. Rider 将方案 + Riding Record 提交至 ARY
  2. ARY 用假数据和假环境进行 沙箱验证 ——检查是否存在死循环、病毒、硬 bug
  3. 验证通过后，ARY 转发 至 Organizer 侧
  4. Organizer 持有真实数据，完成评测，返回评分
  5. ARY 公示成绩/排名（组间仅此可见）
- 数据边界：
  - Rider 提交的方案包含什么：产品定义、功能描述、系统设计、Agent 协同记录
  - Rider 提交的方案 不包含 什么：完整 Race 私有数据、Organizer 内部评审依据、未经披露的项目材料
  - ARY 不会缓存 Organizer 的真实数据集用于后续评测——数据不可用时，评分无法完成，显示缺失
- 安全机制：沙箱验证确保方案不会对 Organizer 侧造成威胁；真数据只在 Organizer 手中，ARY 不持有不缓存。

#### UC-R10 查看成绩与排名

- 主流程：
  1. Organizer 评分后，ARY 公示成绩和排名
  2. 各组可看到自己的分数、排名位置、排行榜
  3. 各组 看不到 其他组的方案、Riding Record、提交内容——组间隔离
  4. 有权限者（评委、Organizer）可查看完整内容
- 数据边界：评分和排名是公开的；方案和过程记录是各组的隐私资产——类似 GitHub private repo，只有被授权者能看。

| FR-R3 | 自动抓取骑行日志（时间戳 + 工作内容），汇聚为组内贡献面板 | UC-R2~R6 |
| FR-R4 | Agent 集成入口——Rider 能在 ARY 内启动和使用 Agent | UC-R3~R6 |

## 4. 数据类型与数据主权分类

### 4.1 Rider 拥有的数据

| 数据 | 说明 |
| --- | --- |
| 项目需求 | Organizer 披露的唯一公开数据 |
| Agent 原始输出 | Rider 的 Agent 会话记录 |
| 组内其他 Record | 全透明可查 |
| 留言板沟通记录 | 组内提问 + 评委回复 |
| 本组方案（未提交） | 各组隐私 |

### 4.2 Rider 不拥有、不可访问的数据

| 数据 | 说明 |
| --- | --- |
| 完整 Race 私有定义 | 在 Organizer 侧 |
| 真实测试数据 | 在 Organizer 侧，仅供评测 |
| 评测内部逻辑 | 在 Organizer 侧 |
| 其他组的方案和 Riding Record | 组间隔离的隐私资产 |
| 完整协作原文 | 仅在 Organizer 侧（如果 Organizer 选择不公开） |

### 4.3 Rider 提交后可查看的数据

| 数据 | 说明 |
| --- | --- |
| 本组评分和排名 | 来自 Organizer 评测 |
| 排行榜前几名 | 按 Organizer 要求公示 |
| 骑行日志汇总面板 | ARY 自动汇总，组内防造假 + 贡献判断 |

### 4.4 数据流向总表

| 流向 | 内容 | 条件 |
| --- | --- | --- |
| Organizer → Rider | 项目需求 | 无条件 |
| Rider → ARY | 方案 + Riding Record | 提交时 |
| ARY → Organizer | 方案 | 沙箱验证通过后 |
| Organizer → ARY | 评分 | 评测完成后 |
| ARY → Rider | 成绩/排名 | 评测完成 |
| Rider ←→ 组员 | Riding Record、互评、留言板 | 组内全透明 |
| Rider ←→ 评委/Organizer | 留言板沟通 | Agent 可代劳 |
| 其他组 → Rider | 仅排行榜排名 | 组间隔离 |
| ARY 自动 | 骑行日志抓取、面板汇聚 | 持续 |

## 5. 安全机制（Rider 视角）

1. 数据可用性实验（Rider 参与版） ：Rider 提交方案后，如果 Organizer 侧数据不可用，评分无法完成——ARY 显示"数据缺失"。这证明 ARY 没有缓存真实数据进行评测。
2. 沙箱验证 ：ARY 用假数据和假环境验证方案的安全性（死循环、病毒、硬 bug），确保传给 Organizer 的方案不会造成威胁。
3. 组间隔离 ：方案和 Riding Record 是各组隐私资产。组间只公示成绩和排名。抄袭风险的源头被切断——你无法看到别人怎么骑。
4. 防造假 ：ARY 自动抓取骑行日志 + 时间戳，汇聚为贡献面板。事后伪造 Riding Record 几乎不可能——时间线和内容一致性会被自动检查。
5. Agent 可代劳全流程 ：从协作评论到留言板提问，Agent 可以辅助完成——但日志会区分"Agent 代发"和"人手动操作"，不做虚假骑行。
6. 展示边界 ：Rider 侧的页面不展示 Organizer 私有数据、真数据路径、评测内部逻辑和完整协作原文。只展示 Rider 自己能感知的状态。
