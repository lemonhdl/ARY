## 表格_20260604

| 评估维度 | 验收项 | 验收方法（可量化、可验证） |
| --- | --- | --- |
| 1. 问题定义是否被真正理解 | ✅ 明确本次 PoC不是做普通赛事系统，而是验证「ARY 不持久化数据也能完成赛事全流程」<br>✅ 明确排除范围：赛事执行、指导骑行、成果评审、复盘<br>✅ 明确核心目标是用 ARY 的方法验证 ARY 本身（self-dogfood 理念） | 1. 检查产品定义部分，是否体现出对本次Racing的独到理解，是否偏离本次Racing核心<br>2. 检查功能需求部分，是否增添过多非本次Racing核心关注点 |
| 2. 产品逻辑是否成立 | ✅ 完整覆盖赛事创建→披露→组织→展示全流程<br>✅ 所有流程最终都能追溯到「数据在 Organizer 侧」<br>✅ 无逻辑矛盾：ARY 不存受限/私有数据但能正常运行 | 1. 走查完整流程，确认每个环节都符合数据流向设计<br>2. 模拟异常场景（如Organizer 断网）（根据时间安排可动态调整是否模拟这个场景）<br> |
| 3. 去中心化数据主权是否清楚 | ✅ 明确 Race 数据100% 归 Organizer 所有<br>✅ 明确 ARY无任何数据所有权和控制权<br>✅ 明确展示内容仅来自 Organizer主动披露的公开投影 | 1. 检查系统设计文档，确认数据主权边界描述<br>2. Demo演示 Organizer 对数据的绝对控制权（修改、撤回、删除等）<br>3. 根据小组成员挖出的Rider的数据安全相关内容，在Demo中演示 |
| 4. PoC 是否证明了关键假设 | ✅ 证明 1：Race 数据可以完全留在 Organizer 侧<br>✅ 证明 2：ARY不持久化Organizer侧受限数据和完整Race私有数据。<br>      ARY页面和存储中不应包含私有材料、完整协作原文、I内部评审依据等受限内容。<br>✅ 证明 3：ARY 仍能完成创建、披露、组织、展示<br>✅ 证明 4：展示内容仅来自 Organizer 主动披露 | 1. 实验性证明（核心）：   <br>    - 实验 1：Organizer 修改数据→ARY 实时更新   <br>    - 实验 2：Organizer 撤回数据→ARY 立即消失   <br>    - 实验 3：清空浏览器缓存 + 重启 ARY→无任何数据残留<br>    - 实验 4：根据Rider的具体数据安全可扩展相关证明<br>2. 代码审计：确认 ARY 无任何文件写入、本地存储代码 |
| 5. 架构边界是否清晰 | ✅ 明确划分 Organizer、ARY、ARY三个角色的职责<br>✅ 无职责交叉：ARY 只做展示和流程编排，不做受限/私有数据存储和写入<br>✅ 所有数据流向清晰：Organizer→ARY→用户 & 用户→ARY→Organizer | 1. 检查系统架构图，确认三个角色边界清晰<br>2. 抓包验证：所有数据请求均指向 Organizer，ARY 无受限/私有数据写入请求 |
| 6. 展示是否清晰让别人看得懂 | ✅ 完整展示路径：Race 列表→Race 详情→Riding Record→Record Detail→Replay<br>✅ 未提交时不显示评测结果，提交后进入评测状态<br>✅ 数据不可用时明确显示「数据已被主办方撤回」<br>✅ 页面不暴露内部路径、API 地址、JSON 原始响应 | 1. 手动走查所有展示页面，确认流程闭环<br>2. 检查未提交和已提交状态的显示差异<br>3. 模拟数据不可用场景，验证页面提示<br>4. 检查页面源码和网络请求，确认无内部信息泄露 |
| 7. 与 Agent 的协作过程是否可追踪、可解释、可复盘 | ✅ Riding Record 完整覆盖9项 Agent Riding Skill：目标设定、任务拆解、Agent <br>      协同、过程观察、方向干预、技术判断、架构理解、计划管理、结果验收<br>✅ 明确区分人的决策和 Agent 的输出 | 1. 查看过程节点，说明人和 Agent 的分工<br>2. 查看 Agent 的原始输出和人工修改痕迹 |
