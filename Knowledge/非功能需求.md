# 非功能需求

> 来源：飞书文档《非功能需求》；同步日期：2026-06-06；revision: 4。
> URL：https://ncnodbu72igv.feishu.cn/docx/HCocdduTgolJcNxcqLKcQjRlnje

本节描述 ARY GRS 001 在功能实现之外必须满足的质量属性与约束条件。由于本次 Race 的核心目标是证明“Organizer 侧受限数据不被 ARY 中心化持久化保存时，ARY 仍能完成 Race 展示、Riding Record 组织与过程回放”，因此本节重点围绕数据安全、去中心化数据主权、可验证性、展示清晰度和可演进性展开。

## 5.1 数据安全与去中心化数据主权

### 需求说明

ARY GRS 001 的核心非功能要求是保证 Race 数据的主权归 Organizer 所有。Organizer 是 Race 数据的唯一主权方，负责定义赛事、决定公开范围，并保留完整 Race 私有数据。ARY 不应成为完整 Race 私有数据的中心化存储方，而应作为公开内容的组织、索引和展示平台。

在本项目中，数据可分为三类：

1. 受限数据，永驻 Organizer 侧 包括完整 Race 私有定义、Organizer 私有材料、完整 Agent 协作原文、内部评审依据、未公开项目材料、未发布内容等。这些数据不应被 ARY 持久化保存，也不应出现在 ARY 的公开展示页面中。
2. 公开披露数据，可由 ARY 展示 包括 Race 基本信息、Riding Record 摘要、Replay 关键事件和本次提交状态。这些内容必须来自 Organizer 主动披露，而不是 ARY 默认从完整私有数据中自动抽取。
3. 受控数据，可保存但需权限保护 包括参赛者提交、队伍资料、阶段性成果和未公开评审内容。这类数据可以在必要场景下被系统使用，但应受到权限控制，不能作为公开内容直接展示。

当 Organizer 侧受限数据不可用时，ARY 不应通过历史缓存、持久化副本或预置结果继续完成评测或展示受限结果。ARY 可以展示公开内容，但不能持有和继续使用 Organizer 未授权或已撤回的受限数据。

### 验收方式

- 检查 PRD 和系统设计中是否明确区分受限数据、公开披露数据和受控数据。
- 检查 ARY 页面是否未展示完整 Race 私有定义、Organizer 私有材料、完整 Agent 协作原文和内部评审依据。
- 在 PoC 中验证：当 Organizer 侧数据不可用时，ARY 显示数据缺失，而不是继续展示历史评测结果。
- 在 PoC 中验证：当 Organizer 侧数据再次不可用后，ARY 重新显示缺失，证明平台没有将受限数据保存为长期可继续使用的数据。

## 5.2 数据最小化与公开披露边界

### 需求说明

ARY 在组织和展示 Race 时，应遵循数据最小化原则。平台只应保存和展示完成 Race 公开披露、Riding Record 组织、Replay 回放和本次提交状态反馈所必需的数据，不应为了实现展示功能而收集完整 Race 私有数据。

在 Race 展示层，ARY 只需要展示 Race 名称、简介、状态、生命周期、公开标签等基本信息。在 Riding Record 展示层，ARY 只需要展示经过 Organizer 允许披露的 Record 标题、摘要、关键步骤、Replay 事件和 Riding Signal。

对于完整 Prompt 历史、完整 Agent 输出、内部评审依据、私有材料路径、未公开任务细节和未发布内容，ARY 不应保存或展示。公开披露内容应由 Organizer 主动决定，而不是由 ARY 默认获取或长期保存。

对于参赛者提交数据，ARY 只应在本次提交和评测状态反馈中使用必要内容。页面可以显示“未提交”“数据缺失”“评测完成”等状态，但不应暴露评测过程中的内部数据、完整受限材料或 Organizer 侧服务细节。

### 验收方式

- 检查 Race 页面是否只展示公开 Race 信息，而不是完整 Race 私有定义。
- 检查 Riding Record 和 Replay 是否只展示公开摘要和关键事件。
- 检查提交状态页面是否只展示本次提交状态，不展示内部评测过程和受限材料。
- 检查页面是否没有出现私有材料路径、内部评审规则、完整 Agent 协作原文等内容。

## 5.3 可验证性

### 需求说明

ARY GRS 001 的数据安全要求不能只停留在设计说明中，而应能够通过 PoC 的可观察行为被验证。评审者应能够在不查看内部代码或数据库实现的前提下，通过页面状态变化理解 ARY 没有将 Organizer 侧受限数据持久化为长期可继续使用的数据。

本 PoC 通过提交与评测状态的变化来验证数据边界：

1. 未提交时，页面不显示任何评测结果，证明结果不是平台预置内容。
2. 当参赛者提交内容但 Organizer 侧受限数据不可用时，页面显示数据缺失，证明 ARY 无法脱离 Organizer 侧数据独立完成评测。
3. 当 Organizer 侧数据可用时，ARY 可以显示本次评测结果，证明平台能够在授权或可用条件下使用本次所需数据。
4. 当 Organizer 侧数据再次不可用后，页面重新显示数据缺失，证明 ARY 没有通过历史缓存、持久化副本或预置结果继续使用受限数据。

该验证过程应具备可重复性。评审者可以按照固定路径多次执行“未提交、数据不可用、数据可用、再次不可用”的状态切换，并观察页面结果是否符合预期。

### 验收方式

- 打开提交页面但不提交，页面应不显示评测结果。
- 在 Organizer 侧数据不可用时提交，页面应显示数据缺失。
- 在 Organizer 侧数据可用时提交，页面应显示本次评测结果。
- 在 Organizer 侧数据再次不可用后重新提交，页面应重新显示数据缺失。
- 重复以上流程，结果应稳定一致。

## 5.4 可理解性与展示清晰度

### 需求说明

ARY 的页面和交互应让参赛者与评审者清楚理解本项目的核心定位：ARY 是面向 Agent Riding Race 的平台，而不是普通题解提交或在线评测系统。因此，页面主线应围绕 Race 展示、Riding Record 组织、Record Detail 和 Riding Replay 展开，提交与评测状态只作为数据边界验证的一部分，不应成为平台表达的中心。

Race 首页应清楚说明 GRS 001 的主题、Race 状态和平台定位，使用户进入系统后能够理解本次 PoC 要证明的问题。Riding Records 页面应突出 Agent Riding 过程资产，而不是只展示提交结果或分数。Record Detail 页面应帮助用户理解一次 Riding 中的 Prompt、Agent Output、Steering 和 Riding Signal。Replay 页面应通过事件流展示 Rider 如何观察、判断、干预和验收 Agent。

页面文案应面向参赛者和评审者，避免使用过多开发者视角的技术表达。对于数据缺失、评测完成、未提交等状态，页面应使用清晰的业务语言说明当前发生了什么，而不是展示接口错误、服务名称、终端命令或内部调试信息。

### 验收方式

- 手动走查 Race 首页、Records、Record Detail、Replay 和提交状态页面。
- 检查页面是否突出 Agent Riding Record，而不是排行榜、刷题或普通 OJ。
- 检查未提交、数据缺失、评测完成等状态是否使用清晰业务语言表达。
- 请未参与开发的同学阅读页面，确认其能理解 ARY 的平台定位和 PoC 证明路径。

## 5.5 可回放性

### 需求说明

ARY 应支持对 Agent Riding 过程的回放与复盘。Riding Record 不应只记录最终结果，而应展示 Rider 在任务推进过程中的关键操作和判断，使评审者能够理解 Rider 如何设定目标、观察 Agent 输出、进行方向干预并完成验收。

Record Detail 页面应展示一次 Riding 中的关键过程信息，包括 Prompt、Agent Output、Steering 和 Riding Signal。Replay 页面应按照事件流组织 Riding 过程，使用户能够按时间顺序理解一次 Agent Riding 是如何展开的。

同时，可回放内容应遵守数据披露边界。Replay 中展示的应是 Organizer 允许公开的过程摘要和关键事件，而不是完整 Agent 协作原文、私有材料或内部评审依据。

### 验收方式

- 检查 Record Detail 是否包含 Prompt、Agent Output、Steering 和 Riding Signal。
- 检查 Replay 是否按事件流展示 Riding 过程。
- 检查回放内容是否能体现目标设定、任务拆解、过程观察、方向干预、结果验收等关键 Agent Riding Skill。
- 检查 Replay 是否未暴露完整私有协作原文或 Organizer 私有材料。

## 5.6 页面表达边界

### 需求说明

ARY 的公开页面应避免暴露内部实现细节或可能造成误解的调试信息。页面展示内容应面向参赛者和评审者，而不是面向开发人员。

在 Race 首页、Riding Records、Record Detail、Replay 和提交状态页面中，不应出现内部路径、文件名、版本指纹、JSON 快照、服务请求细节、终端操作提示、debug 信息或未公开材料名称。这些信息可能削弱页面的产品完成度，也可能暴露 Organizer 侧或 ARY 侧的内部实现细节。

当系统出现数据不可用、未提交或评测未完成等状态时，页面应使用清晰的业务状态说明，而不是直接展示接口错误或底层服务异常。

### 验收方式

- 检查所有公开页面，确认没有内部路径、文件名、JSON 原始响应、版本指纹或 debug 信息。
- 检查错误和缺失状态是否使用业务语言表达。
- 检查页面是否未暴露 Organizer 侧服务地址、内部请求参数或终端操作提示。
- 检查公开页面是否未出现未公开材料名称。

## 5.7 可演示性

### 需求说明

ARY GRS 001 的 PoC 应具备清晰、稳定的演示路径。评审者应能够在较短时间内通过连续点击理解系统主线和数据安全证明过程。

PoC 的核心演示路径应包括 Race 首页、Riding Records 列表、Record Detail、Replay 页面和提交状态页面。演示过程应能够展示“未提交无结果、数据不可用显示缺失、数据可用显示本次结果、再次不可用后重新显示缺失”的状态变化。

每个页面都应有明确的证明点，避免依赖大量口头解释。演示过程应控制在 3 到 5 分钟内，保证评审者能够快速理解 ARY 的产品定位、Agent Riding Record 的价值以及受限数据不被平台长期持有的证明逻辑。

### 验收方式

- 按固定演示路径走查所有核心页面。
- 确认 3 到 5 分钟内可以完整讲清楚 Race、Record、Replay 和数据边界证明。
- 检查每个页面是否有明确证明点。
- 确认演示过程不依赖终端、代码或内部调试信息才能理解。

## 5.8 可扩展性与可演进性

### 需求说明

当前 PoC 使用本地 Node 服务、JSON 数据和 mock 提交来验证关键假设，这些实现方式只服务于本阶段的概念证明，不代表最终生产系统形态。

后续系统可以将本地 JSON 数据替换为真实数据库或对象存储，将 mock 提交替换为正式提交表单、文件上传和队伍权限系统，将单独的数据可用性模拟进程替换为真实 Organizer 服务或授权接口。

在后续演进中，系统仍应保持 Organizer、Rider 和 ARY 之间的边界清晰。PoC 阶段的简化实现不应破坏核心架构原则：Organizer 控制受限数据，ARY 组织和展示公开内容，Rider 通过平台参与 Race 并查看被允许公开的 Riding Record 和 Replay。

### 验收方式

- 检查文档中是否说明当前 mock 实现只服务于 PoC。
- 检查后续替换方向是否保持 Organizer、Rider、ARY 的职责边界。
- 检查演进方案是否仍坚持受限数据由 Organizer 控制、公开内容由 ARY 展示。
- 检查是否没有为了 PoC 简化而引入与数据主权冲突的设计。
