# ARY GRS 001：Product Definition

# 数据安全的 Race

在 Race 数据存留于 Organizer 侧、ARY 不持久化 Race 数据的前提下，ARY 如何完成赛事的创建、披露、组织与展示？

必须证明：

1. Race 数据可以存留在 Organizer 侧
2. ARY 不需要持久化保存完整 Race 数据
3. ARY 仍然可以创建、披露、组织、展示赛事
4. 展示内容来自 Organizer 主动披露的公开元数据或公开投影

不在本次 PoC 范围内：

赛事执行，包括指导骑行、成果评审、骑行复盘等，由其他 ARY 子系统实现，不在本 PoC 内，不是 GRS 001 的核心证明对象

重点不是写一份普通 PRD，而是让 ARY 有一个能够证明关键假设的 PoC

# 你们将如何参加？

Race Flow：从组队到复盘

你们不是只提交最后答案。你们要展示自己如何骑行智能体完成任务

流程如下：

1. Race Brief：理解本次挑战和要求
2. Team Build：完成组队，1 coach + 4 到 5 riders
3. 工具准备：完成 Claude、DevCompass Racing 等相关工具安装，接入 ARY 执行核
4. Riding Plan：制定骑行计划，完成方案和 PoC
5. Co-Riding：与 Agent 协同
6. Checkpoint：中途检查与指导
7. Submission：提交作品、文档与过程记录，提交到 GitHub Classroom
8. Review & Replay：评审、复盘、展示与改进，下周一

# 我们如何看待优秀作品？

我们从 7 个维度综合评估，寻找真正具备价值、可落地、可演进的智能体作品

7 个维度包括：

1. 问题定义是否清楚
2. 产品逻辑是否成立
3. 去中心化数据主权是否被真正理解
4. PoC 是否证明了关键假设
5. 架构边界是否清晰
6. 展示是否让别人看得懂
7. 与 Agent 的协作过程是否可追踪、可解释、可复盘

我们不只看你“做出了什么”，我们也看你“如何骑行智能体把它做出来”
