# 1 项目概述

## 1.1 项目名称

ARY - Agent Racing Yard 智能体竞赛平台

本项目以 ARY Genesis Race Series 001 为原型，围绕 Agent Riding Record 的组织、展示与评测展开，探索智能体时代下“人如何驾驭 Agent 完成任务”的竞赛平台形态。

## 1.2 项目背景

随着大语言模型和 Coding Agent 的快速发展，软件开发、文档整理、数据分析和复杂任务执行正在从“人直接完成任务”逐渐转向“人驾驭智能体完成任务”。在这种工作方式下，最终结果不再是唯一值得评价的对象。参赛者如何提出目标、约束智能体、根据中间输出进行纠偏、验证结果，同样体现了重要的能力。

然而，现有多数竞赛平台仍以最终提交物、测试结果和排行榜为核心，难以展示人机协作过程中的关键决策。对于 Agent 相关竞赛而言，如果只展示最终答案，评审难以判断参赛者是否真正具备 Agent Riding 能力，也难以复盘一次任务是如何被完成的。

此外，智能体竞赛可能涉及赛事材料、评测依据、组织方数据和未公开规则。部分数据不适合直接上传到平台集中保存。平台需要在支持赛事组织、过程展示和结果反馈的同时，尊重组织方对数据披露范围的控制。

ARY 正是针对这一背景提出的智能体竞赛平台。它希望把参赛者与 Agent 的协作过程组织成可展示、可回放、可评价的 Riding Record，并在此基础上探索更适合 Agent 时代的竞赛组织方式。

## 1.3 现有主流产品分析

为了明确 ARY 的定位，我们对当前与编程竞赛、智能体工具、模型评测和协作记录相关的产品形态进行了分析。

### 1.3.1 在线编程评测平台

以 LeetCode、HackerRank、Codeforces 等平台为代表，在线编程评测平台提供了成熟的题目发布、代码提交、自动评测和排行榜机制。

优势分析：

- 评测流程清晰：参赛者提交答案后，平台能够快速返回结果。
- 竞赛组织成熟：题目、提交、结果和排名等环节已经形成稳定模式。
- 反馈效率高：自动评测能够支持较大规模的参赛者同时参与。

局限性分析：

- 关注最终答案：平台主要评价代码或结果，对完成过程关注较少。
- 过程不可复盘：评审难以看到参赛者如何分析问题、调整策略和验证结果。
- 不适合 Agent Riding：无法表达参赛者如何通过 Prompt、反馈和纠偏驾驭智能体完成任务。
- 数据组织方式集中：平台通常默认题目、测试和评测数据由平台集中管理，不适合所有数据安全场景。

ARY 需要保留“提交后评测”的清晰流程，但核心不应是普通题解和排行榜，而应是 Agent Riding 过程本身。

### 1.3.2 Coding Agent 工具

以 Claude Code、GitHub Copilot、Cursor 等工具为代表，Coding Agent 工具可以帮助用户完成代码生成、调试、重构、文档编写和项目推进。

优势分析：

- 交互自然：用户可以通过自然语言给出目标和约束。
- 能力广泛：能够参与开发、分析、文档和验证等多类任务。
- 适合真实项目：支持多轮交互和持续调整，贴近实际软件工程过程。

局限性分析：

- 缺少竞赛组织能力：工具本身不负责发布赛事、组织参赛者或展示结果。
- 过程记录分散：Prompt、输出和纠偏记录往往停留在会话中，缺少统一结构。
- 难以横向评价：不同参赛者的 Agent 使用过程缺少统一展示和比较方式。
- 不面向评审展示：原始会话通常不适合直接作为课程或竞赛的展示材料。

ARY 可以借鉴 Coding Agent 的协作过程，但需要把这种过程整理为结构化的 Riding Record，使其能够被组织、展示和评价。

### 1.3.3 AI Benchmark 与 Agent 评测平台

现有 AI Benchmark 或 Agent 评测平台通常用于比较模型或智能体在特定任务上的表现，例如代码生成、网页操作、工具调用和任务完成率等。

优势分析：

- 指标明确：通常能够给出准确率、完成率、耗时或成本等量化结果。
- 便于比较：适合横向比较不同模型或 Agent 的能力。
- 研究价值高：有助于分析智能体在特定任务上的能力边界。

局限性分析：

- 评价对象偏向模型：平台更关注模型表现，而不是人如何驾驭模型。
- 人类 Steering 不突出：用户的目标设定、过程纠偏和结果验证往往不是核心评价对象。
- 展示方式偏实验：不一定适合课程项目或竞赛平台的可点击展示。
- 数据披露边界不明显：许多评测默认数据和评测逻辑集中在评测环境中。

ARY 的目标不是单纯比较模型强弱，而是评价参赛者与 Agent 的协作过程。它更关注“人如何让 Agent 完成任务”。

### 1.3.4 协作文档与项目管理工具

以飞书文档、Notion、GitHub Issues、Linear 等工具为代表，协作文档和项目管理工具可以记录项目讨论、任务分工和交付材料。

优势分析：

- 适合沉淀过程：可以保存讨论、文档、决策和复盘内容。
- 协作能力强：团队成员可以共同维护项目资料。
- 展示形式灵活：适合撰写 PRD、报告和总结材料。

局限性分析：

- 不是竞赛平台：缺少 Race、参赛者、提交、评测和回放等结构化对象。
- 依赖人工整理：过程记录需要人工维护，难以自动形成可评价材料。
- 缺少统一交互：评审需要在多个文档之间切换，难以获得完整平台体验。
- 缺少评测闭环：无法直接承担提交、评测和结果反馈流程。

ARY 可以与文档工具配合，但平台本身需要提供统一的赛事入口、过程展示和评测反馈，而不是只依赖文档说明。

### 1.3.5 市场空白与机会

通过对比可以发现，现有产品大多分别覆盖了“代码评测”“Agent 使用”“模型评测”或“协作文档”中的某一部分，但缺少一个面向 Agent Riding 竞赛的统一平台。

当前主要空白包括：

1. 过程展示不足：现有竞赛平台主要展示结果，难以展示人如何驾驭 Agent。
2. 评价对象不清：现有 Agent 评测更多评价模型能力，而不是参赛者的 Riding 能力。
3. 记录结构分散：原始会话和项目文档难以直接转化为可评价的竞赛材料。
4. 数据边界不足：部分平台默认集中持有数据，不适合组织方需要控制数据披露范围的场景。

ARY 正是针对这些问题，尝试构建一个以 Riding Record 为核心的智能体竞赛平台。

## 1.4 项目目标

本项目旨在开发一个面向 Agent Riding Race 的平台原型，支持赛事组织、过程展示、提交评测和数据边界控制。其核心目标是构建一个能够体现 Agent Riding 能力的竞赛平台，而不是普通的编程题评测网站。

具体目标包括：

- 展示 Agent Riding 过程：将参赛者与 Agent 的协作过程整理为 Riding Record，使评审能够看到目标设定、Agent 输出和人类纠偏。
- 支持过程回放：通过事件化的方式展示一次 Riding 过程，帮助评审理解任务推进路径。
- 组织智能体竞赛：提供 Race、Record、提交和评测等基本竞赛对象，形成完整的平台体验。
- 强调数据安全边界：在平台展示和评测过程中，避免直接暴露未公开材料和评审依据。
- 提供可交付原型：实现一个可运行、可点击、可演示的 PoC，用于验证 ARY 平台的核心价值。

本阶段项目重点在于验证 ARY 的产品方向和关键交互，而不是实现完整商业化平台。更细粒度的功能需求、页面交互、数据流、系统模型和验收标准将在后续章节中展开。
