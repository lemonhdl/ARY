# ARY 真实交付状态清单

版本：v0.1  
状态：草案 / 用于集成前核实四组交付现状  
适用范围：A Rider 客户端、B 管理系统、C 前端展示、D 数据层、E 整合统一  

## 1. 文档目的

本文用于回答一个非常具体的问题：

当前仓库里，哪些交付物是真实存在、已提交、可直接消费的；哪些只是设计说明；哪些在文档中被声明存在，但当前仓库快照里没有检索到。

这份清单的用途不是评价谁做得好坏，而是降低整合误判，避免把“文档里的计划”当成“仓库里的现货”。

## 2. 判定口径

### 2.1 状态枚举

| 状态 | 含义 |
| --- | --- |
| `已提交，可直接消费` | 仓库中存在具体文件，整合人现在就可以读取或接线 |
| `已提交，可演示但非正式契约` | 仓库中存在具体文件，但更偏原型、样例或演示资产，不应直接视为正式生产 contract |
| `已提交，仅文档说明` | 仓库中只有设计说明、任务说明或评审文档，尚无对应实现/数据产物 |
| `文档声明存在，但当前仓库未检索到` | 文档写明存在相关产物，但当前仓库快照中未找到对应文件 |
| `待负责人确认` | 当前无法仅靠仓库确定，需负责人补充说明 |

### 2.2 说明

1. 本文只基于当前仓库快照判断，不推断负责人本地未提交文件。
2. “未检索到”不等于绝对不存在，只表示当前仓库内不可见、整合人当前不可直接使用。
3. 对“可直接消费”的判断以整合视角为准，不以作者主观完工感为准。

## 3. 当前总览

### 3.1 当前最可用的真实交付

当前仓库里最接近“可直接用于第一轮集成”的交付，集中在以下内容：

1. `design-prototype/` 下的高保真原型页面。
2. `design-prototype/data/sample-races.json` 与 `sample-races.js` 样例数据。
3. `docs/` 下的产品、领域、IA、权限、QA、OPS、CA 契约文档。
4. `tasks/` 下的四组分工说明、复核建议、共享字段字典。

### 3.2 当前最明显的空缺

当前仓库里尚未看到以下类型的真实交付：

1. 可运行的正式应用壳代码。
2. Rider 客户端实现或可执行回放脚本。
3. 管理系统实现代码或独立 mock。
4. 数据层文档中声称存在的 `data/` 目录及其脚本、schema、种子数据。
5. 统一的管理端 dashboard 数据源和 CA 健康读取模型。

## 6. 当前不应被误判为“已可直接集成”的内容

以下内容当前不应被当作“已经在仓库里、可以直接接线”的事实：

1. Rider 客户端代码已经存在。
2. Admin Console 代码已经存在。
3. 数据层 `data/` 目录及其脚本、schema、种子文件已经提交。
4. 已有正式应用壳、正式路由或正式部署配置。
5. 已有统一的管理端读取模型或 CA 健康 mock。

为了让整合真正进入实施阶段，建议每组负责人尽快补充以下最小事实：

2. 是否能先提交 3 条事件样例和 1 条失败样例。

2. 是否能冻结发布态和可见性规则。

2. 是否能把页面依赖字段整理成 adapter 输入要求。

### 7.4 D 组

1. `data/` 目录是否真实存在但未提交。
2. 是否能先提交最小的 JSON 导出，而不是等待完整数据库工程。
3. 哪些文档里提到的产物是计划中，哪些是已完成但未提交。

### 7.5 E 组

1. 尽快建立统一 mock 数据文件。
2. 尽快建立 adapter 层，把原型数据和后续真实数据源映射到共享字段字典。
3. 在统一 mock 跑通后，再决定是否迁移到正式应用壳。

## 8. 当前结论

当前仓库最真实、最可用的交付是“文档基线 + 高保真原型 + 原型样例数据”。

如果现在就推进集成，最稳妥的路线不是等待所有组员补齐完整实现，而是：

1. 继续以 `design-prototype/` 为第一轮产品壳。
2. 以 `tasks/ARY-shared-field-dictionary.md` 为共享 view model。
3. 以本文为交付真实性校验基线。
4. 让 A、B、D 三组先补最小可提交样例，而不是继续只写长文说明。
