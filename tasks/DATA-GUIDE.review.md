# 数据层分工复核与补充建议

## 1. 结论

这份文档的信息量很大，数据建模、生成、验证、导出、联调思路也相对完整。从设计质量看，它是有体系的。

但从当前仓库现状看，必须先指出一个关键事实：文档中反复提到的 `data/` 目录、`manage.py`、`environment.yml`、`seed.sql`、`sample-races.generated.json` 等关键交付物，目前在仓库里没有检索到。也就是说，现阶段它更像“计划中的数据层交付说明”，而不是“已可供整合直接消费的现状说明”。

这个差异本身就是后续集成的首要风险。

## 2. 合理之处

1. 把事实源和读取模型分层是对的，符合 `Projection` 不是事实源的总体原则。
2. 明确覆盖报名、RaceProject、CA、Session、Work、Judging、Award、Evidence、Report 的事实链，这对后续整合很有帮助。
3. “前端导出 JSON 与数据库种子并行产出”的思路合理，能同时服务展示端和后台。
4. `verify` 思路很好，说明作者意识到数据层不能只停留在 mock。

## 3. 主要缺口

### 3.1 文档现状与仓库现状不一致

这是最大问题。文档使用了很多“已生成”“已存在”“可直接运行”的表述，但当前仓库中没有对应产物。后续整合时必须先区分：

1. 已提交到仓库的真实交付物。
2. 本地存在但未提交的交付物。
3. 仍处于设计中的交付物。

如果这三类不分开，整合人会误判可用性。

### 3.2 交付面过宽，职责容易越界

文档同时覆盖：

1. 数据库生命周期管理。
2. 领域 schema。
3. 全量样例数据生成。
4. 前端兼容导出。
5. GitHub 登录身份存储。

这套范围本身可行，但已经接近“后端基础设施 + 数据平台 + mock 工程”而不只是“数据指南”。后续要防止该模块继续吞并应用层职责。

### 3.3 缺少外部消费 contract

虽然文档描述了很多表，但对整合更重要的是：

1. 前端展示端实际稳定读取哪些 JSON 字段。
2. 管理端 dashboard 读哪些聚合字段。
3. Rider 侧联调时哪些字段可回放。

现在这些信息分散在长文里，不利于多人并行接线。

### 3.4 缺少 schema 版本和变更策略

如果这套数据层后续真的推进，多人集成时至少要有：

1. schema 版本号。
2. 生成数据版本号。
3. 破坏性字段变更说明。
4. 导出 JSON 的兼容承诺。

## 4. 建议补充

### 4.1 先补一份“交付真实性清单”

建议新增一张简表，把每个产物分为：

| 产物 | 状态 | 位置 | 整合可直接使用 | 备注 |
| --- | --- | --- | --- | --- |
| schema SQL | 已提交 / 未提交 / 设计中 | 路径 | 是 / 否 | |
| seed SQL | 已提交 / 未提交 / 设计中 | 路径 | 是 / 否 | |
| 前端 JSON 导出 | 已提交 / 未提交 / 设计中 | 路径 | 是 / 否 | |
| 管理脚本 | 已提交 / 未提交 / 设计中 | 路径 | 是 / 否 | |

### 4.2 从长文里抽出 3 个小 contract

建议另外沉淀成独立短文或 schema：

1. `frontend-export-contract`：给展示端用。
2. `dashboard-read-model-contract`：给管理端用。
3. `ca-replay-fixture-contract`：给 Rider/服务端联调用。

### 4.3 第一轮只承诺最小可运行数据面

建议第一轮只要求这 4 个实际可交付产物：

1. 一份可提交的前端 JSON。
2. 一份可读的关系型 JSON。
3. 一份字段级 schema 说明。
4. 一组校验通过的最小样例数据。

数据库生命周期管理脚本如果还不稳定，可以暂时降级为第二优先级。

### 4.4 把“验证口径”分成强校验和说明性统计

当前文档已隐含这样做法，但建议显式写出：

1. 强校验：不通过即不能交付。
2. 说明性统计：用于评估覆盖度，不作为阻断条件。

## 5. 对整合的直接影响

这份分工如果补齐真实交付状态，会成为整合阶段最关键的基石之一；如果不补，反而会成为最大误导源，因为它看起来“最完整”，但当前仓库里看不到对应实体产物。

因此建议先做两件事：

1. 核实并提交最小数据产物。
2. 把长文中真正供别人消费的 contract 单独抽出来。
