# Rider 客户端分工复核与补充建议

## 1. 结论

这份分工的边界意识是四份里最强的一份，尤其是“不把 GitHub Repo 伪装成骑行数据”“不公开原始 Session”“不接受赛后补造实时证据”这几个点，都和总文档基线一致。

但它目前仍偏“协议意图说明”，还没收敛成集成时可落地的客户端契约。最大问题不在功能项够不够，而在这些关键环节还没有定死：

1. 登录与会话绑定协议。
2. 签名 canonicalization 规则。
3. push / retry / replay 的时序约束。
4. 客户端断网、重启、升级时的行为。

## 2. 合理之处

1. `W1-W9` 的职责切分基本正确，覆盖了登记、传输、抓取、幂等、防伪和失败上报。
2. 对“实时信号 push + 完整快照 fetch”双通道的理解和 `docs/ary-ca-integration-spec.md` 一致。
3. 对“不做事项”的梳理有价值，能减少 Rider 端被不断加码。
4. 明确说明只支持 Claude Code，这对 MVP 是合理收敛。

## 3. 主要缺口

### 3.1 签名设计仍停留在原则层

文档确认了“消息要签名”，但真正能联调还缺：

1. 签名算法最终选型。
2. 待签名字节串的 canonicalization 规则。
3. 签名字段放在 body 还是 header。
4. 验签失败的响应码和重试规则。
5. 时间戳、nonce、sequence、幂等键之间的共同约束。

没有这些，服务端和客户端各自实现后极容易互不兼容。

### 3.2 登录与鉴权边界含混

文档里写了 GitHub 登录，但当前仓库对登录相关能力的另一个分工在数据/平台侧。这里需要明确：

1. Rider 客户端是否自己发起 GitHub OAuth。
2. 还是只消费平台发下来的短期 token。
3. 登录态和 `caConnectionId` 绑定到哪个层级：`user`、`registration` 还是 `raceProject`。

### 3.3 缺少本地可靠投递策略

如果要做成真实可演示产品，客户端必须写清楚：

1. 本地是否持久化消息队列。
2. 断网后是否补发。
3. 重启后如何恢复 `sequence`。
4. 哪些失败可重试，哪些失败必须放弃并告警。

### 3.4 缺少版本兼容规则

当前只写了接口依赖，没有写：

1. 客户端版本号如何上报。
2. 服务端不兼容时如何拒绝。
3. 事件 schema 升级时如何兼容旧客户端。

## 4. 建议补充

### 4.1 先冻结 MVP 协议四件套

建议先产出 4 个固定文档或 schema：

1. `register-handshake` 请求/响应。
2. `push riding signal` 请求头、请求体、签名规则。
3. `fetch session snapshot` 协议。
4. `error code` 与 `retry policy` 表。

### 4.2 签名方案直接给出 MVP 定稿

如果本轮目标是顺利集成，而不是密码学研究，建议 MVP 直接定：

1. 使用 `Ed25519`。
2. 对固定 canonical JSON 字节串签名。
3. 签名值放 HTTP Header，同时 body 内保留 `messageId`、`timestamp`、`sequence`。
4. 服务端按 `caConnectionId + messageId` 做幂等，按 `sequence` 做乱序检测。

### 4.3 增加本地状态机

建议把客户端状态明确为：

`idle -> authenticated -> registered -> handshaken -> streaming -> degraded -> stopped`

并规定每个状态允许的动作与可恢复路径。

### 4.4 增加整合需要的最小交付件

即便暂时没有完整代码，也建议交付给整合人：

1. 事件 schema 示例。
2. 3 组签名样例。
3. 失败场景样例。
4. 一份本地假数据回放脚本或录制文件。

## 5. 对整合的直接影响

这份分工适合作为 `DEV-5` 的客户端侧输入，但如果不补协议定稿，整合阶段会出现两个高风险点：

1. 服务端和 Rider 客户端各自“看起来都对”，但实际验签或重放处理不兼容。
2. 前端 Live Hall 想接实时数据时，不知道哪些字段是最终稳定字段。

因此，建议把下一步重点放在“冻结协议”，而不是继续扩写背景说明。
