# ARY GRS 001 Product Definition 评审标准

## 一、评审目标

**ARY GRS 001：Product Definition** 的评审重点，不是看谁写了一份更漂亮的 PRD，而是看参赛团队是否能够围绕 ARY 的核心命题，提出清晰的产品定义、合理的系统方案，并通过关键技术 PoC 证明：

> 在 Race 数据存留于 Organizer 侧、ARY 不持久化 Race 数据的前提下，ARY 仍然可以完成赛事的创建、披露、组织与展示。

本次 Race 评审的是学生作为 **智能体工程师 / Agentic Engineer** 的综合能力，包括产品理解、系统思考、技术验证、表达展示，以及与 Agent 协同完成真实创造的 **Agent Riding Skill**。

------

## 二、硬性入围门槛

作品必须满足以下 4 个基本条件，才进入正式评分：

### 1. 不能违背 ARY 的数据主权原则

作品必须明确体现：

- Race 数据主权属于 Organizer；
- Race 源数据存留在 Organizer 侧；
- ARY 不作为 Race 数据的中心化持久化存储平台；
- ARY 只消费 Organizer 主动披露的公开元数据或公开投影数据。

如果方案默认把完整 Race 数据都存进 ARY 中央数据库，则不符合 GRS 001 核心命题。

### 2. 必须有可解释的 Product Definition

作品不能只是技术 Demo，必须说明：

- ARY 是什么；
- GRS 001 要解决什么问题；
- Organizer、ARY、Participant、Audience 等角色如何参与；
- Race 如何被创建、披露、组织与展示。

### 3. 必须有关键技术 PoC

作品必须提供能够运行或清楚演示的 PoC，用来证明关键假设，而不是只停留在概念图或 PPT。

PoC 不要求完整实现 ARY，但必须能证明核心链路成立。

### 4. 必须提交 Riding Record

作品必须保留与 Agent 协同完成任务的过程记录，体现学生如何规划、提问、判断、干预、修正与验收。

没有过程记录的作品，不能完整体现 Agent Riding Skill。

------

## 三、100 分制评分标准

## 1. 问题理解与产品定义｜15 分

评审重点：是否真正理解 ARY GRS 001 的产品命题。

评分要点：

- 是否准确理解 ARY 是智能体时代的软件开发训练场、竞技场；
- 是否准确理解 ARY 作为去中心化智能体赛事平台的定位；
- 是否准确理解 GRS 是 ARY 的 self-dogfood 系列赛事；
- 是否清楚说明 GRS 001 为什么聚焦 Product Definition；
- 是否能把抽象命题转化为具体产品场景；
- 是否清楚定义目标用户、核心角色与使用路径。

高分作品特征：

> 不是简单复述概念，而是能把 ARY、GRS、Organizer 数据主权、Race 披露与学生参与场景组织成一个清晰、可信、可验证的产品方案。

------

## 2. 去中心化数据主权与系统架构｜20 分

评审重点：是否真正证明“数据留在 Organizer 侧，ARY 仍然可以工作”。

评分要点：

- 是否清楚区分 Organizer 侧数据与 ARY 侧公开数据；
- 是否说明 Race 源数据、公开元数据、公开投影数据分别是什么；
- 是否有清晰的数据流图或系统架构图；
- 是否说明 ARY 如何索引、展示、引导参与，而不是持久化完整 Race 数据；
- 是否说明 Organizer 如何控制披露范围；
- 是否考虑数据安全、权限边界、更新机制与失效状态；
- 是否避免把 ARY 设计成传统中心化赛事平台。

高分作品特征：

> 能清楚表达 “Public Yard, Private Race Source” 的架构：ARY 是公共骑场，Organizer 掌握 Race 源数据，ARY 只展示被披露的数据与入口。

------

## 3. 关键技术 PoC 有效性｜25 分

评审重点：PoC 是否真正证明了 GRS 001 的核心假设。

评分要点：

- 是否能演示 Race 在 Organizer 侧被创建；
- 是否能演示 Organizer 向 ARY 披露公开元数据或公开投影；
- 是否能演示 ARY 展示 Race 列表、详情、状态或入口；
- 是否能演示 ARY 不依赖自身持久化保存完整 Race 数据；
- 是否能说明 PoC 中哪些数据在哪里保存；
- 是否有最小可运行 Demo、接口模拟、数据样例或原型系统；
- 是否能处理基本异常情况，例如 Organizer 数据不可访问、披露数据过期、Race 下线等；
- 是否清楚说明 PoC 的边界与未实现部分。

高分作品特征：

> PoC 不一定复杂，但必须击中关键问题：只要 Organizer 侧数据仍在，ARY 就能通过公开披露数据完成赛事发现、组织入口与展示；ARY 不需要成为 Race 数据中心。

------

## 4. 赛事创建、披露、组织、展示体验｜10 分

评审重点：方案是否让人看得懂、用得起来、参加得进去。

评分要点：

- Race 创建流程是否清楚；
- Race 披露页面是否清楚；
- 学生或参赛者如何发现 Race；
- 如何报名、进入、参与或查看 Race；
- Race 状态、规则、成果、入口是否被合理展示；
- 页面或 Demo 是否具备基本可用性；
- 是否体现 ARY 的训练场、竞技场气质；
- 是否能让外部观众快速理解这场 Race 是什么。

高分作品特征：

> 不只是后端逻辑成立，还能让 Organizer、学生、观众都理解“这场 Race 怎么被看见、怎么被参加、怎么被展示”。

------

## 5. Agent Riding Skill 与过程质量｜20 分

评审重点：学生是否体现了智能体工程师的工作方式。

评分要点：

- 是否有明确的 Riding Plan；
- 是否能把复杂任务拆解给 Agent；
- 是否能识别 Agent 产出的错误、遗漏与幻觉；
- 是否有中途干预、修正、重构和验收过程；
- 是否能利用 DCR 或其他过程记录方式呈现协同过程；
- 是否能说明哪些部分由 Agent 完成，哪些部分由人判断；
- 是否体现计划、观察、干预、验收、复盘的完整闭环；
- 是否能从过程记录中看出团队真实学习与成长。

高分作品特征：

> 不是“让 AI 一次性生成答案”，而是像智能体骑手一样，持续观察、判断、干预、调整，让 Agent 朝正确方向前进。

------

## 6. 文档、表达｜10 分

评审重点：是否能把复杂方案讲清楚。

评分要点：

- 文档结构是否清晰；
- 产品定义、架构、PoC、过程记录是否完整；
- 图表是否帮助理解，而不是装饰；
- 是否能用简洁语言解释自己的方案；
- 是否能诚实说明方案限制与下一步计划。

高分作品特征：

> 不需要猜，就能快速理解：你解决了什么问题，怎么解决，证明了什么，还没证明什么。

------

# 四、加分项

以下内容不作为硬性要求，但可以在同等条件下加分：

### 1. 协作质量突出

团队分工清楚，1 coach + 多名 riders 的协作方式有效，过程记录完整。

### 2. Demo 表现有冲击力

展示页面或 Demo 有明显 ARY 气质，体现 “Ride Agents. Build the Future.” 的未来感与竞技感。

### 3. 边界意识清楚

能够清楚说明：

- GRS 001 做什么；
- GRS 001 不做什么；
- 赛事执行、指导骑行、成果评审、骑行复盘为什么不在本次 PoC 范围内；
- 未来如何与 DCR 或其他 ARY 子系统衔接。

### 4. 可扩展性强

方案不仅能支撑课堂 100 人 Race，也能解释未来如何扩展到更多课程、Hackathon、公开赛事或高校联赛。

### 5. 复盘质量高

不仅展示成功结果，也能诚实分析失败、偏差、修正过程与下一轮改进方向。

------

# 五、一票否决项

出现以下情况，原则上不能获得高分，严重时可直接判定不合格：

1. 方案把完整 Race 数据默认集中存储到 ARY；
2. 没有任何可运行、可演示或可验证的 PoC；
3. 没有提交 Riding Record 或过程记录；
4. 作品无法解释 Organizer、ARY、Race 数据之间的关系；
5. 明显抄袭、伪造过程记录或伪造 Demo 结果；
6. 使用 Agent 生成内容后没有任何人工判断、修正和验收；
7. 无法说明本次 PoC 与“数据安全的 Race”之间的关系。

------

# 六、评分等级建议

## S 级｜90–100 分

作品完整、清晰、有说服力。
不仅证明了关键假设，还能让人看到 ARY 未来产品与技术架构的雏形。PoC 有效，系统边界清楚，Agent Riding 过程扎实，展示效果优秀。

## A 级｜80–89 分

核心命题理解准确，PoC 能证明主要假设，架构与产品定义较清楚。过程记录较完整，有明确的 Agent Riding Skill 体现。

## B 级｜70–79 分

基本理解 GRS 001 命题，有一定产品定义和技术 PoC，但系统边界、数据主权、Demo 完整度或过程记录存在明显不足。

## C 级｜60–69 分

完成了基本提交，但更多停留在概念描述。PoC 证明力不足，或对 Organizer 数据主权、ARY 非持久化原则理解不够清楚。

## D 级｜60 分以下

未能回答 GRS 001 的核心问题，或没有有效 PoC，或方案明显违背 ARY 的去中心化数据主权原则。

------

# 七、建议奖项设置

除了总分排名，可以设置以下特色奖项：

1. **Best Product Definition**
   最佳产品定义奖：奖励对 ARY / GRS 001 理解最清楚、产品逻辑最完整的团队。
2. **Best Decentralized Architecture**
   最佳去中心化架构奖：奖励最清楚证明 Organizer 数据主权与 ARY 非中心化存储边界的团队。
3. **Best PoC**
   最佳技术验证奖：奖励 PoC 最有证明力、最清楚击中关键假设的团队。
4. **Best Agent Riding**
   最佳智能体骑行奖：奖励 Agent 协作过程最清晰、干预最有效、复盘最扎实的团队。
5. **Best Demo Experience**
   最佳展示体验奖：奖励最容易被学生、Organizer、观众理解和使用的展示方案。
6. **Genesis Rider Award**
   创世骑手奖：奖励在 ARY GRS 001 中表现出强烈探索精神、协作精神和未来工程师气质的学生或团队。

------

# 八、评审核心句

评审最终要回答一个问题：

> 这个作品是否证明了：
> **Race 数据可以留在 Organizer 侧，而 ARY 仍然能够完成赛事的创建、披露、组织与展示？**

同时也要回答第二个问题：

> 这组学生是否展现出了智能体工程师应有的 **Agent Riding Skill**？
